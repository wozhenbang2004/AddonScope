# 首次开源发布与公测计划

首发围绕一个可验证结果：单独正常、组合失败时，用户能看清依赖与真实导入来源，
在副本中复现并缩减失败组合，把证据交给维护者。先做清楚的实验性工具，再扩大
能力。1,000 Star 是传播目标，不是代码完成后自然到账的奖励。

完整工程路线见 [ROADMAP](ROADMAP.zh-CN.md)，发布条件见
[RELEASE_CHECKLIST](RELEASE_CHECKLIST.md)。本文件是计划，不表示已发布或已联系任何人。

## 首发交付

| 交付 | 内容 | 如何检查 |
| --- | --- | --- |
| 可安装版本 | 0.3.0 Alpha扩展ZIP、源码包、校验和 | 用最终ZIP实际安装/启用/扫描/卸载；从源码包独立恢复 |
| 首次使用入口 | 中英文README、短安装路径、当前原生界面图 | 新用户无需额外背景即可找到安装和扫描 |
| 可重复示例 | 受控共享wheel冲突、设置敏感失败、标明身份的历史/derived材料 | 命令能运行，结果和已知边界可核对 |
| 求助闭环 | 插件内完整证据、显式历史/比较、可选支持ZIP | 不逼用户导出才能看；分享材料先审隐私 |
| 维护入口 | 问题模板、贡献指南、安全说明、发布工作流 | 链接、版本、包内容与权限匹配 |
| 事实边界 | 兼容矩阵、未验证平台、复现类型、已知限制 | 不把Linux、合成fixture或Python CI扩大成全平台效果 |

先并行完成独立模块，再集成并验证同一个最终包。发现真实阻塞问题就修复和复验；
非阻塞建议进入后续版本。不要为了赶首发同时加入自动修复、任意DLL隔离和完整
场景录制。

## 首发材料

- 一段短演示：两个生成测试插件单独成功，一起失败；显示版本归属、实际导入来源和复验结果。
- 一张只包含AddonScope原生面板的清晰截图；caption标明版本和测试数据身份。
- 一份机制说明：引用Blender共享wheel源码，解释命名空间、Python导入与原生库的不同边界。
- 一份支持ZIP示例：让维护者判断需要哪些信息，明确日志分享前需要检查。
- 有条件时加入得到授权的真实插件端到端案例；否则清楚标出历史材料或derived最小复现，不冒充完成。

Alpha首发可公开请求Windows/macOS和真实插件组合的验证。请求验证不等于已经支持，
公开故障的历史修复也不能写成当前产品缺陷。

## 发布与反馈顺序

1. 发布GitHub仓库与Alpha prerelease，确认附件可下载且README中的安装步骤有效。
2. 先请少量插件作者或有明确失败组合的用户试用，收集安装失败、误报和无法复现结果。
3. 在允许工具分享的Blender社区发布一次有复现内容的说明，清楚写出边界和希望得到的反馈。
4. 按真实案例写技术复盘，给出修复前后条件；未经许可不公开插件文件、配置和私密日志。
5. 优先解决首次成功和诊断质量，再用实际反馈选择0.4以后的切片。

社区入口可以包括Blender开发者社区、插件作者自己的issue/discussion和中英文创作者
社区。每处先确认规则，按受众解释用途；不批量刷帖，不购买Star，不去无关项目互Star。
公开说明由维护者审核后发布；这份计划不表示任何社区消息已经发送。

## 分开记录产品与传播结果

| 信号 | 说明与下一步 |
| --- | --- |
| 访问很少 | 检查标题、演示和合适入口，不能靠继续加功能解决曝光 |
| 下载后不能安装 | 修包格式、安装入口和平台问题 |
| 能安装但没有有效诊断 | 检查扫描覆盖、结果解释和首次任务路径 |
| 有报告但误判/未复现多 | 优先诊断模型、失败身份和复现条件 |
| 有独立项目复用结果 | 获得许可后整理公开案例，扩充有价值的分支 |
| 只有Star增长 | 仍需要采用和诊断效果证据，不能等同产品验证 |

不虚构兼容率、时间节省、用户量或维护者采用。记录真实Star增量、下载、安装失败、
独立诊断报告和复现结果，并保留失败案例。
