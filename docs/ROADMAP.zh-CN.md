# AddonScope 完整迭代路线

路线按诊断任务和可验证结果组织。已交付能力以发行记录为准，后续版本不承诺固定工期。
每个版本先满足验收再发布；真实案例和平台证据可以改变后续优先级。

## 0.3.0 Alpha：诊断与求助闭环

目标：新用户能安装、看懂一条线索、在副本中复现、缩减并确认失败；需要求助时，
把足够的证据交给维护者。发布时明确平台与证据边界。

| 工作线 | 交付范围 | 验收与发布条件 |
| --- | --- | --- |
| 核心诊断 | 扫描、版本对照、实际导入来源；修复有复现依据的分类/设置问题 | 扫描不导入插件；未知结果不冒充冲突；原安装未变化 |
| 试运行 | 工厂设置/当前插件设置；可理解的超时、次数、停止与失败确认 | 同失败指纹和原顺序保留；最后新进程复验；取消不报已确认 |
| 历史与对比 | 用户显式保存诊断、读取历史、对比当前环境 | 数据往返一致；损坏/过大输入有错误；旧导入不伪装成当前观测 |
| 求助材料 | 支持 ZIP 汇总报告、清单、逐次结果和摘要 | 默认路径脱敏；不附插件源码或原始设置快照；可独立打开 |
| 原生体验 | 所有信息在 Blender 内查全；状态、历史、比较和分享入口有主次 | 实际GUI走通首次使用、运行/停止、失败恢复、历史对比与导出 |
| 案例证据 | 受控示例可重复；历史公开故障及derived最小复现有出处 | 不把生成fixture当真实案例；不把已修复历史故障说成当前缺陷 |
| 发布工程 | 版本/许可/包内容一致；CI及发行附件可重复生成 | 从最终ZIP安装/扫描/卸载；从源码包独立恢复；CI未跑标未跑 |
| 公共入口 | 中英文README、已知限制、贡献/安全说明、问题模板、路线 | 所有链接和命令有效；截图是当前版本；不编用户量或效果数字 |

发行验收针对同一份最终源码和安装包。模块检查、实际Blender流程、界面检查和独立审查
分别提供证据，不能用单个模块通过代替整体验收。

**允许首发的最低范围**：Linux + Blender 4.5 LTS 作为已验证环境，其他平台明确
列为待验证；受控和derived示例注明身份。完整第三方插件端到端案例不足时，可以
发布实验性Alpha，但不能宣传成通用兼容工具或已证明的排查提速产品。

**0.3 范围外**：自动替换依赖、自动修改加载顺序、任意DLL隔离、完整场景自动修复、
云账户/付费服务、未经许可的插件再分发。这些不属于按时首发的必要条件。

## 0.3.x：公测修补与平台验证

目标是把首次公开反馈转成真实可复验改进，不急着扩张功能。

- 收集 Windows/macOS 实际安装、启用、扫描、成功/失败probe、超时、停止、卸载记录。
- 修复安装入口、空结果、扫描覆盖、设置恢复、错误归因等阻断首次成功的问题。
- 优先打磨错误解释：先说失败阶段和受影响插件，再列已观察证据、尚未确认的原因及可执行下一步；保留完整异常供维护者核对。
- 以真实求助样例验收修改建议；未验证的版本组合不能写成确定修复，未知原因不能由通用建议掩盖。
- 让至少一名独立使用者或维护者提交可用的匿名化诊断，并记录工具未能解决的情况。
- 用同一平台和输入复测问题；把“未复现”与“已修复”分开。

退出条件：兼容矩阵由运行证据支持，常见首次使用失败有恢复路径，支持材料足以让
别人重现报告。单靠CI绿色或下载量不算达到。

## 0.4：场景与操作复现

目标：解决“注册没报错，真正使用才坏”的问题。

| 切片 | 设计与技术工作 | 验收 |
| --- | --- | --- |
| 显式复现步骤 | 用户选择授权的测试场景和受控操作配方；显示将执行的操作 | 不静默运行任意脚本；取消/超时/上下文缺失可解释 |
| 场景副本 | 在副本中加载测试文件，记录Blender/插件/设置/操作条件 | 原场景不改；未复制的外部资源列出；缺资源不误判冲突 |
| 失败一致性 | 将操作/阶段纳入失败身份，区分注册、场景加载与操作异常 | 缩减不能用另一种报错替代目标故障 |
| 社区案例 | 与维护者一起保留可公开运行的案例与修复前后条件 | 原插件端到端、derived复现和生成fixture始终分开 |

先支持少量明确操作配方，不承诺记录并重放所有Blender交互。后台模式无法覆盖的
界面行为，单独设计有头测试流程。没有足够真实需求就不造通用自动化平台。

## 0.5：依赖关系与加载顺序诊断

目标：解释为什么某个插件被保留，以及注册顺序是否影响故障。

- 提供有来源的必需依赖、固定上下文和候选关系图；用户可核对和修正。
- 在受控副本中比较原顺序与明确选择的替代顺序，每次保留完整实验条件。
- 对顺序敏感、非单调和多个独立故障分别给证据，避免强行输出唯一冲突对。
- 将历史对比扩展为“更新前后发生了什么”，关联包版本、状态、路径与失败身份。

验收：依赖闭包与顺序试验均可单独复跑；图中的关系有具体证据；未知关系不伪装
成确定依赖。自动重排原环境仍不是默认行为。

## 0.6：原生库与崩溃证据

目标：对DLL/SO/ABI问题提供比“文件重名”更有用的证据。

- 按Windows/Linux/macOS分别确认加载器、架构、Python ABI和动态库来源。
- 记录崩溃发生阶段、进程返回信息与可用加载证据；区分启动失败和插件注册崩溃。
- 在明确许可下支持选择性原生诊断工具集成，评估安装成本和平台限制。
- 给维护者可运行的最小原生冲突样例，展示工具能确认的范围与无法判断的部分。

验收：至少有一个对应平台的可重复原生案例；没有该平台执行证据就不宣称支持。
此版本优先诊断，不承诺把任意插件的DLL隔离成互不影响。

## 1.0：稳定诊断工具

1.0 由证据成熟度决定，而不是仅靠功能数量。

| 维度 | 稳定版需要达到的状态 |
| --- | --- |
| 平台 | 明确支持的OS与Blender版本都有实际安装、核心流程和回归记录 |
| 结果 | 证据强度、失败阶段、未覆盖范围一致；严重误判有回归样例 |
| 复现 | 公开案例覆盖共享Python依赖、设置、顺序和至少一类原生问题 |
| 数据 | 历史/支持格式有版本策略、损坏恢复与合理的迁移约束 |
| 体验 | 首次成功、长时间排查、中断恢复和维护者求助都能独立完成 |
| 维护 | 问题模板、发布回滚、可重复构建和安全报告入口可用 |
| 采用 | 有独立项目实际用结果解决问题，并允许公开说明；不把Star替代采用 |

## 每轮如何选择下一步

先处理会造成数据风险、严重误判或阻断核心流程的问题；随后处理真实用户重复
遇到的痛点。新增功能需说明谁受益、现有流程哪里不够、用什么案例验收。没有
这些依据的想法留在候选，不为了版本号或功能数量赶工。

传播与产品改进分开评估：曝光不足看入口与演示；能安装却不能产出有效报告看
首次使用；报告充足却误报多看诊断准确性。1,000 Star 是传播目标，不是质量验收。
